## Gate placement

The current `SuccubusEligibilityCheck` has the same 78-statement opcode sequence and jump targets as the previously mapped CFG in `.test-tmp/shield-cfg-evidence.md`. With the default false flag, a charged, toggled shield intercepts eligibility before the heat category 0 or combo 2,000 test. Enhanced Plating holds the first charge and increments `ShieldBlockCount` from 0 to 1, then consumes a charge and resets the count on the next block. A consumed last charge turns off the shield toggle. The check returns false on every intercepted path. A true `CanSuccubiSpawn?` bypasses the shield path but still goes through heat/combo eligibility. Demon Proof or exorcist cooldown returns false first.

`BP_DrawManager.DetermineCardV2` calls the GlobalManager eligibility filter, heat weight adjustment, combo weight adjustment, shared weighted choice, and event dispatch in that order. Succubus Shield interception therefore belongs at the eligibility filter, before weighted event selection. These findings are static packaged-bytecode and typed CDO evidence; active-round gameplay acceptance remains outstanding.

The shared player now invokes this gate before its supported weighted media events, persists the block counter and toggle, and updates the actual item charges. New shared-player counters start at zero. For the original counter this is an inference from the directly declared child integer, absent CDO override and lack of other initializer writes, together with Epic's documented [automatic UObject property initialization](https://dev.epicgames.com/documentation/en-us/unreal-engine/unreal-object-handling-in-unreal-engine): it is not a directly serialized zero value. The pure gate still requires the caller to pass a counter explicitly, and restored shared-player sessions retain their saved value.
