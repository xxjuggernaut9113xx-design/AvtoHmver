# P-04 — Remote streaming

2026-10-29 iPhone 18 tailnet check: the disposable Server fixture at the
Host's Tailnet address loaded its library and images on a real second device.
The 4-second H.264 fixture video did not play in the browser preview or when
the ID stream URL was opened directly in Safari; the direct page was blank.
Replacing only that disposable clip with H.264 Constrained Baseline, AAC-LC,
and fast-start MP4 did not resolve the direct Safari failure. Locally, the
ID stream returned 200 `video/mp4`, 206 byte ranges, and bytes identical to
the source. This establishes remote image access but leaves remote video
playback unresolved. The fixture was shut down after the check.

Recorded: 2026-09-29. Migrated from the native workflow inventory; historical observations retain their original dates where stated.

validated range seeking, reject redirects/nested playlists/unvalidated mpv URLs. Server now has an additive ID-based `/api/media/{id}/stream` endpoint with RFC 9110 range parity: suffix/unsatisfiable/multi-range/malformed/HEAD edge cases, Accept-Ranges on 416, no body on HEAD error responses, and a bounded stream-metadata cache removing the per-request DB lookup plus double canonicalize on the seek hot path; stream() resolves the authenticated Caller and returns 403 when a Viewer lacks the playback capability. Viewer image and libmpv loads use only the pinned Tailnet ID stream URL returned by `Client::playback_source`; it performs no playlist or redirect expansion. Parser, byte/header, playback-permission and renderer-unavailable tests use disposable state.
