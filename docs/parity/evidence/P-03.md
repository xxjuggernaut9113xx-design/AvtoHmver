# P-03 — Queue/clips

2026-10-01 native virtual-clip playback uses the saved start/end range as
per-file libmpv load options, with clip-relative progress and clamped seeking.
Invalid ranges are rejected. A real libmpv test passed for pause within a
range, its end boundary, and a subsequent physical video without inherited
bounds. Local and remote Wall previews resolve the clip's parent media path.
The [libmpv loadfile interface](https://mpv.io/manual/stable/#command-loadfile)
defines the per-file options used here. Installed Viewer clip acceptance
remains outstanding.

Recorded: 2026-09-29. Migrated from the native workflow inventory; historical observations retain their original dates where stated.

reorder/remove/advance/shuffle/repeat, slideshow and boundaries; clip edit/progress/cancel/error/result. Clip jobs now have a native status UI: creation goes through a dedicated worker lane (never blocking other work), a 3s poller watches GET /api/clip-jobs/{id} (HTTP path preserved on Server), the UI shows running/done/error text, the button is disabled while a job runs, the library refreshes on completion, and a pending job resumes after restart. The native Host additionally drives ffmpeg directly (`desktop/src/clips.rs`): real user-facing cancel kills the encode child and marks the job cancelled with staging cleanup, and `-progress pipe:1` parsing reports live percent into `progress_percent` with a progress bar in the UI; lifecycle/cancel SQL has automated tests. No server-side cancel endpoint exists (browser has none either), so Server cancel remains unimplemented.
